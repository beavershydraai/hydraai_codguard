# [E2.3] Risk features and action choice

**Goal:** the full list of candidate features, where each one comes from, the rules
that keep training and serving identical, and how each order gets its action (two models). Wide on purpose:
E2.4 prunes the features.

**Depends on:** the order data model (`docs/data-model.md`). Diagrams: `docs/diagrams/ml-pipeline.png`,
`docs/diagrams/action-decision.png`.

## Acceptance criteria (`COD_Guard_Epics.md`, E2.3)

> Every order has all signal groups: phone history, address quality, order behaviour, velocity, context, COD
> amount.

## How others build this

Commercial COD / RTO scorers in India score each order at checkout from buyer history (new vs repeat, past
returns), PIN-code return rates, order value, address quality, order time and discount use [1–4]. PIN-code rates
need smoothing because small areas overfit [4]. Vendor accuracy claims are unverified. Fraud systems add velocity
features (orders per entity in short trailing windows) and only use events before the scored event [5].

## Label

One label per order, `is_failed`: did the buyer end up not taking the order?

| Final state of the order | `is_failed` | Source |
|---|---|---|
| Delivered | 0 | `DeliveryOutcome.result = delivered` |
| Refused at the door | 1 | `DeliveryOutcome.result = refused` |
| Buyer unreachable | 1 | `DeliveryOutcome.result = unreachable` |
| Cancelled before shipping because the buyer said "Tôi không đặt" (call or confirmation page) | 1 | `CallOutcome.not_ordered`, `BuyerAction.not_ordered` |
| Cancelled before shipping by the buyer (call or confirmation page) | 1 | `CallOutcome.cancelled`, `BuyerAction.cancel` |
| Cancelled because the deposit was not paid | row dropped; if the shop ships anyway, the delivery result is the label | order status after `DecisionAction.require_deposit` |
| Carrier or shop issue | row dropped | `DeliveryOutcome.result = carrier_issue, shop_issue` |
| No final state yet | row dropped | |

The prediction is P(`is_failed` = 1) for the order, over its whole life until a final state, not over a fixed
time window. How long delivery takes is not known when the order arrives, so it is not a feature.

## Grain: one row per order, as of `placed_at`

| Grain | Verdict | Why |
|---|---|---|
| **Order, as of the moment it was placed** | **Chosen** | The decision (ship, link, call, deposit) is made per order at intake, and the label is per order |
| Customer × day | No | One day can hold several orders with different outcomes, and the score is needed before the day ends |
| Customer × month | No | Aggregates over the month include the future of early orders |
| Customer, lifetime | No | One static score per phone; a new phone gets nothing |

`placed_at` is the reference time, not a feature. The model sees what is derived from it (hour, weekday, sale day)
and every history window is measured back from it. `features.parquet` keeps `order_id`, `shop_id` and `placed_at`
as key columns for joins and the time split; they are not model inputs.

## Point-in-time rules

1. **Exclude the current order** from every aggregate.
2. **Two clocks.**
   - *Activity* features count other orders with `placed_at < t`.
   - *Outcome* features count only final states known before t (`delivery.occurred_at < t`, or the cancellation
     time). An order placed earlier but still open counts as activity, never as an outcome.
3. **t** = the order's `placed_at` in training, now in serving.
4. **Encodings** (failure rate by ward, province, shop, SKU) are fitted on the training snapshot only. Training
   rows use out-of-fold values (folds split by time); serving uses the full-snapshot values shipped in
   `models/v{n}/`.
5. **Label maturity:** leave out orders placed in the last 14 days before the snapshot cut-off; their final state
   may not be reported yet.
6. **Split train and test by time**, never at random.
7. Smoothed rates: `(failed + m·p0) / (n + m)`, with `p0` = failure rate of the training snapshot and `m = 5`.

## From catalog to model (E2.4)

1. Compute every feature for every training row; save `features.parquet`.
2. Drop features that are constant, more than 95 % missing, or suspiciously strong (leakage check).
3. Train with a time split; prune by SHAP importance and validation lift.
4. Keep for each surviving feature its `SignalGroup` and Vietnamese label, so `top_signals` and the reasons
   (E3.3) can name it.

## Actions: Model 1 (risk) and Model 2 (uplift)

Diagrams: `docs/diagrams/ml-pipeline.png` (orders → features → two models, training and serving) and
`docs/diagrams/action-decision.png` (how each order gets its action, and when a tier switches to Model 2).

A call or a link changes whether the buyer takes the order, so contacted and uncontacted orders cannot be
treated alike. Two models share the features from `compute_features`:

| | Model 1 · risk | Model 2 · S-learner |
|---|---|---|
| Answers | How likely is this order to fail? | Which action costs the least for this order? |
| Inputs | features | features + `action` (none / link / call / deposit) |
| Learns from | every labelled order | only orders in the random slice |
| Used for | P(fail) → tier, reasons, hard rules | the action, in tiers switched to Model 2 |
| Available | from day one (E2.4) | per tier, once the tier passes the check below |

Model 2 is called once per action with the same features and picks the action with the lowest expected cost:
P(fail | action) × cost of one failed delivery + cost of the action.

### Random slice

Uplift can only be learned from similar orders that received different actions [6, 11, 12]; a fixed
tier → action rule never produces them. So 10–15 % of orders get an action drawn at random among the tier's
options; the rest follow the tier rule. Every order keeps its protection.

| Tier | Actions drawn at random |
|---|---|
| Low | none: always ship |
| Medium | ship / link / call |
| High | link / call |
| Very High | call / deposit |

Each order stores `contact_action` and `action_probability`. Hard rules and contact-protection rules apply
first, and a shop can switch its random slice off.

### Switching a tier to Model 2

Checked every day, for each tier separately:

1. Each action in the tier has at least one failed and one delivered order with a final state; otherwise wait.
2. Train Model 2 on the older random orders.
3. On the newer random orders, estimate the saving per order of "Model 2 picks" over "tier rule" with a doubly
   robust estimate: the model's predicted cost, corrected by the real cost on orders whose drawn action matches
   the policy, divided by the draw probability [13].
4. Put a betting confidence sequence around the saving. Costs are bounded (0 to one failed delivery plus the
   dearest action), so it stays valid at any sample size and when checked daily [14, 15].
5. Whole interval above 0: switch the tier. Otherwise keep the rule and collect more.

After a switch, 85–90 % of the tier's orders follow Model 2 and 10–15 % stay random. The check keeps running; if
the interval falls below 0, the tier goes back to the rule.

### Why the S-learner

- Random draws keep the actions balanced within a tier, so the X-learner's advantage for unbalanced groups [7]
  does not apply.
- One model uses all random orders, which matters with little data, and is the simplest to train and ship.
- It had the best Qini in the largest recent benchmark [9]; no learner wins everywhere [7].
- Known weakness: trees can under-use the action column and shrink the effects towards 0 [7]. The check above
  catches it; the fallback is the X-learner. Several actions with different costs follow [8].

### Prototype and approvals

- E2.2 generates the random slice and action effects that differ by customer type, so the demo can show the Qini
  curve, the chosen action per order and the saving against the tier rule.
- Switched tiers replace the tier → action table (E4.2, a domain rule in `AGENTS.md`), and `RiskScore` may gain
  per-action probabilities (API contract). The repo owner must agree.
- Open: deposit-unpaid orders are dropped from the labels, so P(fail | deposit) learns only from buyers who paid
  and looks better than it is.

## Monitoring and retraining (prototype, after E2.4)

Not in `COD_Guard_Epics.md` yet: needs the repo owner's OK before it is built (AGENTS.md sends new ideas to the
roadmap). Planned for 14–15 Oct, after the first model (M2, 13 Oct), before the feature freeze (M3, 16 Oct).

A daily Cloud Run job, started by Cloud Scheduler, checks data and models with Evidently (open source,
Apache-2.0) [10] and writes an HTML and JSON report to `monitoring/{date}/` in the bucket. The same job runs the
tier check for Model 2 above.

Demo: there are no real delivery results yet, so the demo feeds the job a few synthetic days from E2.2, one of
them with injected drift and lower performance, and shows the report and, with `auto`, the retrain it starts.

| Check | Data | Evidently | If it fails |
|---|---|---|---|
| Data quality | Yesterday's `scoring.features` vs the production model's `features.parquet` | data summary tests: missing values, types, ranges | Alert. Never retrain on broken data |
| Drift | Same, plus the predicted P | `DataDriftPreset` | Alert only; drift alone does not mean the model got worse |
| Performance | Orders whose final state arrived in the last 14 days, with the P they were scored with | `ClassificationPreset`: PR-AUC, lift at top 20 %, calibration overall and per tier | Retrain trigger when the confidence interval of the metric lies wholly below the model's own validation value |

One switch, `RETRAIN_MODE`:

- `on_demand` (default): the report and alert only; a person starts the training job.
- `auto`: a failed performance check starts the training job. The new model is still promoted only if it beats
  the current one on the evaluation gate.

Evidently changed its API in 0.7; pin the version and check the imports against its docs.

## Assumptions to verify

Numbers and choices made in this document without data behind them. Revisit each once real or synthetic data
exists.

| Assumption | Used in | Basis |
|---|---|---|
| Smoothing weight `m = 5` | rule 7 | Common default for additive smoothing; not tuned |
| Label maturity of 14 days | rule 5 | Guess at the slowest normal delivery; replace with the p95 of delivery time in the data |
| Windows 1h / 24h / 7d / 30d / 90d / all | catalog | Common in fraud velocity features [5]; not tuned for COD |
| Night = 22:00–06:00 | `is_night` | Practitioner guides name late-night orders as higher risk [4]; the hours are a guess |
| Sale days = day equals month (9/9, 10/10, 11/11…) | `is_double_day` | Vietnamese marketplace sale calendar; effect unverified |
| Drop features more than 95 % missing | E2.4 step 2 | Rule of thumb |
| Failed orders are a minority (a few % to ~20 %, shop-dependent) | E2.4 metrics | Not verified for Vietnam; the synthetic rate is set by E2.2 |
| Random slice of 10–15 % | Actions | Team choice: smaller is gentler on shops but slower to learn |
| Actions drawn per tier | Actions | Judgment: only actions acceptable for that tier's risk |
| 14-day window for performance | monitoring | Guess at how long final states take to arrive; tune on real data |
