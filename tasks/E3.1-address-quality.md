# [E3.1] Address quality — plan

**Goal:** for every order, score how complete the delivery address is, flag vague addresses, and recognise
old administrative names (before the 1 July 2025 merger) so they can be mapped to the current two-level units.
The output is a structured result that E2.3/E2.4 use as features and E3.3 uses for reasons.

**Spec:** `AGENTS.md` ("Scoring", "Privacy and secrets"), `README.md` (signal table, "Address quality"),
`tasks/E2.3-risk-features.md` (address quality group), `docs/data-model.md` (`address`), `Address` in
`app/schemas/common.py`, `app/risk/features.py` (`has_house_number`).

## Background: the 2025 merger

- Resolution 202/2025/QH15, in force from **1 July 2025**: 63 provinces → **34** (28 provinces, 6 cities).
  The district level (quận / huyện / thị xã / thành phố thuộc tỉnh) was **abolished**. About 10,000 communes
  were merged into **3,321** (phường, xã, đặc khu).
- New address format: `số nhà, đường/ngõ/thôn, phường/xã, tỉnh/thành phố`. Buyers, shops and old saved
  addresses still use the old format for a long time: `..., phường X, quận Y, TP Z`.
- Province mapping (23 merged; the other 11 unchanged: Hà Nội, Huế, Lai Châu, Điện Biên, Sơn La, Lạng Sơn,
  Quảng Ninh, Thanh Hóa, Nghệ An, Hà Tĩnh, Cao Bằng):

- Ward level is harder: one old ward can map to one new ward, or be **split** across several. The new ward
  cannot always be derived from the old name alone; the old district is often needed to disambiguate
  (many provinces had several "Phường 1", "Xã Tân Phú"…).
- **An old name is not a fraud signal.** Many genuine buyers still write the old address. It matters because
  carriers have moved to the new units and an old or mixed address raises the chance of a misrouted parcel
  (`RTO_BAD_ADDRESS`). It gets a small weight in the model and a mild reason, never a strong one.

## Design

### Principle: code decides, Gemini reads

Same rule as for the risk score: **Gemini never sets the address score.** Gemini only reads free text
(parsing, recognising landmarks and vague wording). Code computes the score from verified flags, and every
admin-unit claim from Gemini is checked against the official unit list. A flag that cannot be verified is
dropped, so E3.3 never gets a reason about a ward that does not exist.

```
Address.raw (+ street/ward/province if the shop sent them)
  │
  ├─ 1. Rules (always, no network)      normalise, parse, look up admin units, detect obvious gaps
  ├─ 2. Gemini (optional, cached, capped) parse messy text, detect vague wording / landmarks only
  ├─ 3. Verify                          keep only Gemini parts that match the admin-unit tables
  └─ 4. Score                           code computes score 0–1 from the verified flags
  ▼
AddressCheck  →  order.signals.address (Firestore)  →  features (E2.3), reasons (E3.3), UI (E7.3)
```

If Gemini is down, slow (> 3 s), over quota (E1.4) or disabled, step 2 is skipped and the result is marked
`source = "rules"`. Address checking never blocks or fails order intake.

### Admin-unit data

- Ship a static data file `backend/app/signals/data/admin_units_2025.json`:
  - the 34 new provinces and 3,321 new wards (name, type, code, province);
  - the 63 old provinces and the old district + ward names, each mapped to the new province and to the list of
    new wards it went into (one item = unambiguous; several = split).
- Source: an open dataset built from the official resolutions, for example the `vietnamadminunits` package
  (GitHub `tranngocminhhieu/vietnamadminunits`, about 10,600 old→new mapping rows). Check its licence first.
  Prefer copying its data file with a small build script (`scripts/build_admin_units.py`) over adding the
  package as a runtime dependency. Record the source and date in the file's header.
- Name matching ignores case, diacritics, prefixes (`P.`, `Phường`, `Q.`, `TP.`, `Tp`, `X.`), and common
  aliases (`HCM`, `Sài Gòn`, `SG`, `HN`, `BRVT`, `Vũng Tàu`).

### Output: `AddressCheck`

Pydantic model in `app/schemas/scoring.py` (also used as the stored shape):

| Field | Type | Meaning |
|---|---|---|
| `score` | float 0–1 | Completeness, computed by code (below) |
| `flags` | list[`AddressFlag`] | Verified problems, ordered by weight |
| `admin_format` | `new` \| `old` \| `mixed` \| `unknown` | Which unit system the text uses |
| `province`, `ward` | str \| null | Current (2025) names, when resolved |
| `old_province`, `old_district`, `old_ward` | str \| null | Old names found in the text |
| `ward_candidates` | list[str] | New wards an old ward could map to; more than one = split, ask the buyer |
| `suggested_raw` | str \| null | The address rewritten in the new format, only when the mapping is unambiguous |
| `source` | `rules` \| `rules+gemini` | Whether Gemini was used |
| `version` | str | Rules + prompt version, so cached results can be invalidated |

`AddressFlag` (new enum in `app/schemas/enums.py`; labels are what E3.3 and the UI use):

| Flag | Vietnamese label | Detected by |
|---|---|---|
| `missing_house_number` | Địa chỉ thiếu số nhà | rules (existing `has_house_number`), Gemini for "thôn/ấp/xóm" cases |
| `missing_street` | Địa chỉ thiếu tên đường / ngõ / thôn | rules + Gemini |
| `missing_ward` | Địa chỉ thiếu phường / xã | rules (no ward resolved) |
| `missing_province` | Địa chỉ thiếu tỉnh / thành phố | rules |
| `vague_landmark` | Địa chỉ chỉ mô tả mốc ("gần chợ", "đối diện trường"…) | rules (keyword list) + Gemini |
| `placeholder_text` | Địa chỉ không có nghĩa ("abc", "123", "ko có") | rules + Gemini |
| `unknown_ward` | Không tìm thấy phường / xã này | rules (name not in either table) |
| `ward_province_mismatch` | Phường / xã không thuộc tỉnh / thành đã ghi | rules |
| `old_admin_name` | Địa chỉ dùng tên đơn vị hành chính trước sáp nhập 2025 | rules (old district or old province or old-only ward) |
| `ambiguous_new_ward` | Phường / xã cũ đã tách, chưa rõ thuộc phường / xã mới nào | rules (`ward_candidates` > 1) |

"Delivery instructions" such as "gọi trước khi giao" are not vague on their own; only an address that has
nothing but a landmark is.

### Score (code only)

Start at 1.0 and subtract; clamp to [0, 1]. Initial weights, to be tuned on E3.4:

| Flag | Penalty |
|---|---|
| `placeholder_text` | score = 0 |
| `missing_ward`, `unknown_ward` | 0.35 |
| `missing_house_number` | 0.25 |
| `vague_landmark` | 0.25 |
| `ward_province_mismatch` | 0.25 |
| `missing_street` | 0.15 |
| `missing_province` | 0.10 (0 if the ward resolves to one province) |
| `ambiguous_new_ward` | 0.10 |
| `old_admin_name` | 0.05 |

`backend/config/cod_guard_rules_apac.yaml` already has `address_quality_min: 0.6` (marked ASSUMPTION) for an
"ask the buyer to fix the address" rule; the 0–1 scale keeps that compatible. E3.1 does not change any
decision; using the threshold belongs to E4.2/E4.3.

### Gemini call

- Model from `GEMINI_MODEL`; Vertex AI with ADC (no API key). Region from `GEMINI_LOCATION` (verify the model
  is served in `asia-southeast1`; otherwise `global`, document it in `AGENTS.md` like the Live exception).
- Input: `Address.raw` only. No name, phone or other order data.
- Structured output (`response_schema`) with the parsed parts and the text-only flags (`vague_landmark`,
  `placeholder_text`, `missing_house_number`, `missing_street`), temperature 0.
- The prompt lives in `backend/app/signals/prompts/address.md`, with a version string.
- Cache by `address_key` (normalised raw → hash, as in E2.3) in Firestore `address_checks/{address_key}` with
  `version`. The same address is never sent twice.
- New dependency: `google-genai`. Tests never call the network; the client is injected and faked.

### Where it runs

- `check_address(address, *, gemini=None) -> AddressCheck` in `backend/app/signals/address.py` (pure apart from
  the injected client and cache).
- Called at intake and on an address edit before `compute_features` (E4.1 rescore path). The result is stored
  on the order as `signals.address` (add to `docs/data-model.md`; add `signals` to `NOT_IN_SNAPSHOT` only if the
  snapshot already carries the derived features).
- Features (E2.3): `address_quality_score`, `address_old_admin_name`, `address_vague`, plus the existing
  `address_has_house_number` and `address_parts_filled`. These replace the `gemini_address_*` placeholders in
  the E2.3 catalog.
- `top_signals` keys reuse the flag names (`address_missing_house_number` is already in the API example).

### Train/serve parity

Synthetic training data (E2.2) is large; calling Gemini on every row costs quota and makes training depend on
the network. Options:

1. **Model features from the rules only** (recommended for M2). Gemini output is used for reasons, the UI and
   `suggested_raw`, not as model input. Train and serve compute exactly the same features.
2. Run Gemini once over the unique synthetic addresses, cache, and train on the cached flags. Better signal,
   but more quota and a cache that training depends on.

Start with 1; move to 2 only if E3.4 shows Gemini finds vague addresses the rules miss.

## Out of scope

- Geocoding, map pins, checking that the house really exists.
- Calling a carrier address API (E8.2 may add GHN's ward codes later).
- Changing the address on the order automatically. `suggested_raw` is a suggestion shown to the shop and
  read back to the buyer on the call / confirmation page; only the buyer or staff changes the address.
- Changing the API contract in this PR (exposing `AddressCheck` on `OrderDetail` is a follow-up with E7.3 and
  needs an `api/openapi.yaml` re-export).

## Test cases

Synthetic addresses only (fictional house numbers; real unit names are fine, they are not personal data).

| Input `raw` | Expected |
|---|---|
| `Số 12 ngõ 34 Láng, phường Láng, Hà Nội` | score ≥ 0.9, no flags, `admin_format = new` |
| `12 Nguyễn Trãi, P.2, Q.5, TP.HCM` | `old_admin_name`; old district resolved; new ward or `ambiguous_new_ward` |
| `Thôn 3, xã X, huyện Y, tỉnh Hà Giang` | `old_admin_name`; province → Tuyên Quang |
| `25 Trần Phú, Thủ Dầu Một, Bình Dương` | `old_admin_name`; province → TP Hồ Chí Minh |
| `gần chợ Tân Bình, gọi trước khi giao` | `vague_landmark`, `missing_house_number`, score < 0.6 |
| `abc` / `123` / `ko có` | `placeholder_text`, score = 0 |
| `phường Láng, TP Hồ Chí Minh` | `ward_province_mismatch` |
| `Phuong Lang Ha Noi` (no diacritics) | resolves like the accented form |
| `Số 5, phường Không Tồn Tại, Hà Nội` | `unknown_ward` |
| Gemini returns a ward that is not in the table | that part is dropped; no `rules+gemini` flag invented |
| Gemini times out / raises | result with `source = rules`; intake still succeeds |
| Same address twice | second call served from the cache, no Gemini call |
