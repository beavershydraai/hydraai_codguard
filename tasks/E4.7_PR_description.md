New intake orders now run `load_order → score → assess_order → decide → act` automatically
through ADK before the intake response returns. Two advisory agents assess calibrated model
scores, SHAP contributions and filtered order context before the deterministic decision is
saved. They select evidence-backed Vietnamese reasons; deterministic scoring and policy code
retain control of score, tier and action. Buyer contact channels remain mock until E5 is integrated.

## Changes

- Add ADK 2.x function-node workflows for new orders and contact events, with action routing,
  transient scoring retries (up to three attempts), review fallback and a Firestore decision log.
- Separate intake scoring from persistence: `lifecycle.prepare_score` returns an uncommitted
  snapshot, and `commit_prepared_score` checks the order is unchanged before atomically saving
  the score and deterministic decision after assessment. Keep `score_order` for other callers.
- Run two real ADK `Agent` roles, `risk_analyst` then `evidence_verifier`, using `GEMINI_MODEL`.
  Only canonical Vietnamese reasons backed by numeric features are accepted, with at most
  three reasons. The verifier can only keep or remove the analyst's proposal. Raw personal
  data, free text and decision-writing fields are excluded from the agent contract.
- Add bounded, approximate permutation SHAP of Model 1's complete calibrated failure
  probability. Training retains up to four training feature rows as the background; legacy
  artifacts without a background explicitly report explanations unavailable.
- Cap assessment through atomic shared daily budget claims (default 30 assessment runs per
  UTC day, configurable from 1 to 30 via `ASSESSMENT_DAILY_LIMIT`; failed runs consume quota),
  two LLM requests per run, one HTTP attempt per request and a 15-second agent-workflow timeout.
  Configured assessment errors, invalid output, quota exhaustion and stale snapshots route
  to review before buyer contact. An atomic fallback guard preserves a decision made by a
  concurrent run or staff member, including after a Firestore transaction retry.
- Wire `on_new_order` into `POST /v1/intake/orders`. Repeated intake and repeated sends are
  idempotent; a confirmed order is not contacted again.
- Fix the second AI-call attempt: reserve `order_id:ai_call:1` and `:2`, associate each claim
  with its decision, and record `attempts.ai_call` on the order. No-response handling counts
  those attempts even before E5 writes call records, then moves the order to review.
- Accept `google-adk>=2.11,<3`, with the reproducible lock still resolving the tested 2.11.0.
- Add `shap>=0.48,<1`, locked to 0.53.0, and document the assessment environment settings.
- Document the implementation and remaining integration work in `backend/README.md` and
  `tasks/E4.7_ADK_pipeline.md`.

## Scope and integration status

This PR delivers E4.7's automatic order pipeline with an advisory multi-agent assessment
between scoring and decision persistence. Agent output cannot change the deterministic score,
tier, action, hard rules or contact guards. An assessment receives a copy of scoring and
allowlisted context; it cannot mutate the inputs used to save the decision. The saved scoring
contains SHAP, assessment metadata and validated reasons; the decision log includes the
metadata and reasons.

With `GEMINI_MODEL` unset, assessment records `disabled` and the deterministic flow continues.
Hard-rule and confirmed orders skip the agents; an order without candidate evidence records
`no_evidence`. An untrained risk model leaves the order new and unscored without invoking
assessment. A configured assessment that fails does not authorize contact.

`on_contact_event` is implemented and tested through its runner, but no production endpoint or
scheduled timer invokes it yet. Only the new-order workflow is wired to production intake.
Confirmation-page endpoints remain 501 stubs; real messages, calls and deposit requests belong
to E5. Message composition and voice agents are not part of the assessment module.

## Dependency resolution

`pyproject.toml` now allows `google-adk>=2.11,<3`. `uv.lock` still resolves ADK 2.11.0 to preserve
the tested environment; this is a locked resolution, not an exact requirement in the manifest.

Widening the ADK range permits later 2.x releases; it does not upgrade the lock or remove
constraints from the resolved packages. Later releases may change those constraints and need
renewed validation. The five lower versions remain locked for the following reasons:

| Package | Locked version | Constraint affecting resolution |
|---|---|---|
| `fastapi` | 0.141.1 | 0.143.0 requires `opentelemetry-api>=1.44.0`, conflicting with ADK 2.11.0's cap |
| `google-api-core` | 2.34.0 | 2.42.0 requires `opentelemetry-api>=1.44.0`, conflicting with ADK 2.11.0's cap |
| `websockets` | 15.0.1 | ADK 2.11.0 requires `>=15.0.1,<16` |
| `opentelemetry-api` | 1.42.1 | ADK 2.11.0 requires `<=1.42.1` |
| `tenacity` | 9.1.4 | Locked `google-genai` 2.30.1 requires `<9.2.0` |

Restoring the newer shared versions requires compatible upstream releases. If E5 needs a
newer websockets version sooner, a separate environment for the Live client is an option to
evaluate. Neither dependency isolation nor a further upgrade is implemented in this PR.

Gemini Live compatibility with websockets 15.x remains unverified. E5 must test a real session
for audio streaming, `record_call_outcome` handling and reconnection with the locked dependencies.
The passing mock pipeline tests establish workflow behavior only.

SHAP is locked to 0.53.0 under `shap>=0.48,<1`. The explainer evaluates the classifier plus
isotonic calibration as one function. Its bounded permutation result is marked approximate;
it is separate evidence for explanations and does not modify the model's probability.

## Cold-start follow-up

Intake runs the graph inside the request via `asyncio.run` in a FastAPI worker thread. Its
response time includes storage, scoring, assessment and any scoring retries. The endpoint
stays synchronous while the nodes use blocking Firestore calls.

Cold-start intake latency has not been measured. After the next automatic CI deployment,
measure the first authenticated intake request on a fresh Cloud Run instance/revision using a
synthetic order and a new `external_id`, then compare warm requests. Record the revision,
retry count and response time, and correlate startup logs to confirm the instance was cold.
`/health` latency and local fake-storage timing are not substitutes for that measurement.
