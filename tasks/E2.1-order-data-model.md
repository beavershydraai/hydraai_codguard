# [E2.1] Order data model — plan

**Goal:** one order record used by the backend (Firestore) and by training (Parquet snapshot). The "failed"
label counts buyer-caused failures only.

**Approach:** pure Python functions in `backend/app/data/`, no I/O, fully unit-tested. The backend calls them
before writing to Firestore; the training job (E2.4) calls them to build the snapshot.

**Spec:** `docs/data-model.md`, diagram `docs/diagrams/order-data-flow.png`.

## Acceptance criteria (`COD_Guard_Epics.md`, E2.1)

> One unified order table. The "failed" label counts buyer-caused failures only (refused, unreachable).

## Constraints

- No new dependencies. Test phone numbers use `+84000…` only.
- Branch `feat/e2-1-order-record`, PR `[E2.1] Order record and training label`.
- Each task: write the tests first, then the code; `uv run pytest` and `ruff` pass before committing.

## Tasks

- [ ] **1. Phone normalisation and hashing** (`app/data/phone.py`)
  - `to_e164(raw)`: `0…`, `84…`, `+84…` with spaces, dots or dashes → `+84…`; anything else → None.
    Checks the shape only (9 or 10 national digits).
  - `phone_hash(e164, key)`: HMAC-SHA256 with the secret key.
- [ ] **2. Firestore order document** (`app/data/orders.py`)
  - `order_document(order, order_id, shop_id, phone_key, now)`: `OrderCreate` → `orders/{order_id}` fields
    as listed in the spec: phones normalised and hashed, `placed_at` in UTC, `status = new`.
  - An invalid phone is kept as received, with no hash, so the hard rule can hold the order for review.
- [ ] **3. Delivery result, label, snapshot row** (`app/data/orders.py`)
  - `delivery_fields(outcome, now)`: `DeliveryOutcome` → the `delivery` map to merge into the order.
  - `training_label(result)`: `delivered` → 0; `refused`, `unreachable` → 1; anything else → None.
  - `snapshot_row(doc)`: one flat row for training, without names, raw phones or `scoring`, plus
    `is_failed`; None when the order has no label.
- [ ] **4. Open the PR** once CI is green.
