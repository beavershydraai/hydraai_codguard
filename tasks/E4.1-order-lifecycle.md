# [E4.1] Order lifecycle — plan

**Goal:** every order moves through nine statuses by explicit, tested rules. An edit before shipping
triggers a rescore; an order the buyer confirmed is never contacted again.

**Approach:** pure Python in `backend/app/decision/lifecycle.py` (no I/O, fully unit-tested), next to the
tier policy of E4.2. Services around it read and write the order document in one Firestore transaction.
Intake, the buyer page (E6.1), the call outcome (E5.4), the override (E4.5) and the delivery import (E8.3)
all call the same transition function, so no route sets `status` by hand.

**Spec:** `AGENTS.md` ("Decisions"), `docs/data-model.md`, `OrderStatus` in `app/schemas/enums.py`,
`app/decision/policy.py` (E4.2).

## Acceptance criteria (`COD_Guard_Epics.md`, E4.1)

## Design

### Statuses

| Vietnamese | `OrderStatus` | Meaning | Editable |
|---|---|---|---|
| Mới | `new` | Received; not decided yet (also: no model yet) | yes |
| Được gửi | `cleared_to_ship` | Cleared to ship; not handed to the carrier | yes |
| Chờ xác nhận | `awaiting_confirmation` | A link was sent or an AI call is pending or retrying | yes |
| Chờ cọc | `awaiting_deposit` | Deposit requested | yes |
| Chờ duyệt | `pending_review` | In the manual review queue | yes |
| Đã hủy | `cancelled` | Terminal | no |
| Đã gửi | `shipped` | Handed to the carrier | no |
| Giao thành công | `delivered` | Terminal | no |
| Giao thất bại | `delivery_failed` | Terminal | no |

"Editable" = the order has not shipped, so `PATCH` is allowed. Otherwise 409 `order_not_editable`.

The rule file's `AWAIT_CALL`, `DEFERRED` and `DEFAULT_APPLIED` are not statuses. Waiting for a call is part of
*Chờ xác nhận*; a contact held back by contact hours is a `next_action_at` on the decision.

### Decision → status

| `DecisionAction` | Status |
|---|---|
| `ship_now` | `cleared_to_ship` |
| `send_confirmation_link` | `awaiting_confirmation` |
| `ai_call` | `awaiting_confirmation` |
| `require_deposit` | `awaiting_deposit` |
| `hold_for_review` | `pending_review` |

`cancel` is never an engine action; only a staff override or the buyer cancels.

### Events

| Event | From | To |
|---|---|---|
| `decided` (first scoring) or `rescored` (after an edit) | `new`, `cleared_to_ship`, `awaiting_confirmation`, `awaiting_deposit`, `pending_review` | the table above |
| `buyer_confirmed` | the same five | `cleared_to_ship` |
| `buyer_cancelled`, `buyer_not_ordered` | the same five | `cancelled` |
| `no_response` (last attempt over) | `awaiting_confirmation`, `awaiting_deposit` | what `policy.escalate` returns: still `awaiting_confirmation` for the next call, else `pending_review` |
| `deposit_paid` | `awaiting_deposit` | `cleared_to_ship` |
| `staff_override` | the same five | `cleared_to_ship`, `awaiting_deposit`, `pending_review` or `cancelled` |
| `shipped` | `cleared_to_ship` | `shipped` |
| `delivered` / `delivery_failed` | `shipped` | `delivered` / `delivery_failed` |

Every other pair raises `InvalidTransition`. Terminal statuses have no exit. A repeat of an event that
already happened is a no-op, so a double click or a retried webhook changes nothing.

### Rescore on edit

- Any changed field of `OrderUpdate` triggers one new scoring run; a `PATCH` that changes nothing does not.
- A new phone is normalised and hashed again before scoring.
- Features are computed as of `placed_at`, exactly as at intake, so serving still matches training.
- The previous `scoring` moves to `score_history` (newest first); `scoring`, `tier` and `decision` are replaced.
- The new decision uses the policy version in force now (a policy change applies to later decisions only).
- If staff placed the order in its current state (`decision.decided_by == "staff"`), the status does not
  move automatically; the new score is recorded and shown.

### A confirmed order is never contacted again

- The order stores `confirmation: {at, via}` once: buyer confirms on the page, the call ends *Xác nhận* or
  *Đã sửa*. A staff override is not a confirmation.
- `policy.decide` and `policy.escalate` get a `confirmed` flag. When true, a decision that would contact the
  buyer becomes `ship_now` with block reason `already_confirmed`, and `escalate` returns `None` (timers stop).
- A rescore of a confirmed order still records the new score; the status stays `cleared_to_ship`.
- E4.3 builds the 7-day trust on `confirmation.at`; it adds no second rule here.

### Fields added to `orders/{order_id}`

| Field | Type | Written by | Content |
|---|---|---|---|
| `decision` | map \| null | decide, rescore, override | `Decision` as in the contract: `decided_at`, `action`, `policy_version`, `expected_loss_vnd`, `contact_cost_vnd`, `block_reasons`, `next_action`, `next_action_at`, `decided_by` |
| `score_history` | array of map | rescore | Earlier `scoring` maps, newest first |
| `confirmation` | map \| null | buyer confirm, call outcome | `at`, `via` (`link` or `call`); set once |
| `cancel` | map \| null | buyer cancel, override | `reason` (`cancelled`, `not_ordered`, `shop`), `at`, `by`. `final_state()` already reads it: the two buyer reasons are a failure label, `shop` is not |
| `timeline` | array of map | every event | `OrderEvent` as in the contract |

`contacts` and `calls` stay with E5 and E6.

## Open questions for the owner

1. **Who sets `shipped`?** The contract has no signal that a parcel left the shop; `tracking_code` arrives
   with the result. *Proposal:* a result for a `cleared_to_ship` order passes through `shipped` (two timeline
   events), so *Đã gửi* is only ever visible if we add an explicit "mark shipped" route later.
2. **What marks a deposit paid?** Payments are out of scope, so the demo needs a stand-in. *Proposal:* an
   edit that raises `prepaid_vnd` while `awaiting_deposit` emits `deposit_paid`; the amount still to collect
   drops, as in `AGENTS.md`.
3. **Is *Đã sửa* / `edit_address` a confirmation?** *Proposal:* yes. The buyer saw the order, corrected it
   and the call reads the change back. Otherwise a corrected order would be contacted a second time.
4. **Does a call *Hủy* / *Không đặt* cancel directly?** The rule file (`P02`) wants a confirmation button
   first and adds a state for it. *Proposal:* cancel directly, as the contract and E5.4 describe, and keep the
   button for the rule-file phase.
5. **Shop identity for `PATCH`.** Token verification is not implemented, so a route cannot tell whose order
   it is. *Proposal:* ship the services (tested through the service functions) and leave the route at 501
   until auth lands; do not add auth in this PR.
6. **`delivery_failed` for carrier and shop issues?** *Proposal:* yes, the status says what happened to the
   parcel; the training label still counts only refused and unreachable.
7. **Score history storage** (open question 3 in `docs/data-model.md`). *Proposal:* an array on the order
   (a few runs, about 2 KB each) rather than a subcollection; one transaction covers it.
